# Прогноз оттока абонентов на 30 дней

Можно ли по звонкам, трафику и обращениям в поддержку заранее выделить абонентов, которые уйдут в следующем месяце? В учебном проекте 6‑1 этот вопрос проверен на синтетических данных оператора связи TDG. **В группе из 9 397 абонентов с самым высоким прогнозом риска действительно ушли 2 710 человек.** Доля ушедших в этой группе составила **28,84%** при среднем значении **5,10%** по тестовой когорте.

## Данные и метод

В комплекте TDG уровня S — 200 000 абонентов и 90 дней наблюдений с 1 октября 2025 года. Для каждого абонента конвейер считает активность в двух соседних 14-дневных окнах, её изменение, давность последнего события и число обращений. Дополнительный набор признаков описывает качество сети на основном узле абонента. В выборку входят и абоненты без зарегистрированных звонков. Целевая переменная равна 1, если абонент уходит в течение 30 суток с даты прогноза.

| Назначение среза | Окна активности | Период прогноза | Абонентов | Ушли |
|---|---|---|---:|---:|
| Обучение и выбор модели | 3–30 октября | 31 октября – 29 ноября | 197 486 | 9 553 |
| Итоговая проверка | 2–29 ноября | 30 ноября – 29 декабря | 187 933 | 9 589 |

Для воспроизведения прогноза на прошлую дату у CDR проверяются и время события, и время поступления. Например, звонок 30 октября, доставленный 31 октября, исключается из признаков на начало 31 октября. Поле `retention_contact` исключено из обучения: генератор заполняет его с учётом будущего ухода. Подробности обработки дублей, поздних поставок и повреждённого файла приведены в [отчёте по рефакторингу](refactoring_report.md).

## Выбор модели и результаты

На октябрьском срезе 80% абонентов использованы для обучения, 20% — для выбора модели и порога. Модели сравнивались по **average precision (AP)**: эта метрика показывает, насколько хорошо ушедшие абоненты поднимаются к началу списка риска. Результаты валидации:

| Признаки | Логистическая регрессия, AP | XGBoost, AP |
|---|---:|---:|
| CDR и обращения | 0,1323 | **0,1403** |
| CDR, обращения и телеметрия | 0,1326 | 0,1396 |

Для проверки на следующем месяце выбран **XGBoost с 17 признаками из CDR и обращений**. Добавление телеметрии слегка улучшило результат логистической регрессии, а у XGBoost AP снизилась на 0,0007. Порог 0,12526 был выбран по F1 на октябрьской валидации и зафиксирован перед итоговым тестом.

| AP | ROC-AUC | F1 при выбранном пороге | Точность среди верхних 5% |
|---:|---:|---:|---:|
| 0,2125 | 0,7151 | 0,2837 | 28,84% |

Если ресурсов хватает на контакт с 5% абонентов, такой список охватывает **28,3% всех последующих уходов** (2 710 из 9 589). Вывод относится к одному месяцу синтетического набора. Чтобы оценить, сколько уходов можно предотвратить предложением удержания, понадобился бы отдельный эксперимент.

## Устройство и проверка конвейера

`load_data` проверяет поставку по паспорту и манифесту. `preprocess` строит срезы в DuckDB. `train_model` выбирает модель и порог, а `evaluate` оценивает их на следующем месяце. [Схема этапов и хранения](architecture.md)

Локальный прогон на ZIP и прогон распакованных данных в Docker завершены. Все **8 автоматических тестов** прошли. Повторный запуск Docker сверил контрольные суммы и использовал готовые артефакты. В отдельном контейнере сохранённая модель воспроизвела все тестовые метрики.

## Данные и запуск

Нужен комплект TDG уровня S с `MANIFEST.csv`, `reference/passport.json`, `reference/churn_truth.csv`, суточными CDR, обращениями и телеметрией. Поддерживаются каталог `out` и поставляемый архив `out.zip`. Готовая конфигурация ожидает каталог `../1st_task/out` рядом с репозиторием. Исходные данные предоставляются отдельно.

Из каталога этого репозитория в PowerShell с Python 3.11 или 3.12:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -v
.\.venv\Scripts\python.exe run_pipeline.py --config config.json
```

Свой путь передайте через `--input "D:/datasets/out.zip"`. Для Linux используйте `.venv/bin/python`. В `config.json` задаются пути, номера дней обучения и теста, длина окон и горизонта, доля валидации, seed и параметры моделей. Пути в конфиге отсчитываются от его каталога, аргументы командной строки — от текущего каталога.

## Docker

Команды для PowerShell при запущенном Docker Engine:

```powershell
docker build -t telecom-churn:6-1 .
$dataset = (Resolve-Path ../1st_task/out).Path
$results = (New-Item -ItemType Directory -Force artifacts-docker).FullName
docker run --mount "type=bind,source=$dataset,target=/data,readonly" --mount "type=bind,source=$results,target=/artifacts" telecom-churn:6-1
```

Для дополнительного расчёта с поздними поставками запустите CLI с `--include-late`. В контейнере передайте после имени образа `--input /data --output /artifacts --include-late`. Основной расчёт использует `raw`: генератор не сохраняет момент доставки целой суточной партиции. У отдельного события CDR оба времени, совершения и поступления, должны предшествовать дате прогноза. Для обычных партиций открытие тикета и измерение телеметрии считаются доступными по их времени события.

## Артефакты запуска

CLI печатает путь к завершённому каталогу. Его имя вычисляется из содержимого входа, параметров, версии кода и окружения. Повтор той же команды использует опубликованный результат. Внутри находятся:

| Файл | Содержимое |
|---|---|
| `train.parquet`, `test.parquet` | По одной строке на доступного для прогноза абонента, признаки и метка |
| `model.joblib` | Обученная модель, имена и порядок признаков, порог решения |
| `metrics.json` | Результаты четырёх вариантов на валидации и выбранной модели на тесте |
| `data_quality.json` | Объём источников, обработанные партиции, известные дефекты и размеры когорт |
| `pipeline.log`, `_SUCCESS.json` | Журнал этапов и сведения о завершении, конфигурации и среде |

Схема и разбор фактического запуска приведены в [architecture.md](architecture.md) и [refactoring_report.md](refactoring_report.md).
